# Reflection — effect-internals (2026-09-18, claude)

## Summary

The generator now runs on Effect: Schema-decoded options, Schema.TaggedError
failures formatted at one edge, disk and Biome behind Context.Service layers,
logfmt logs on stderr. Generated output stayed byte-identical across every
commit, checked against 20 captured outputs and two in-repo snapshots. The
PR from refactor/effect-internals is CLEAN with CI green. Verdict: the goal is met; the proof of invariance is
the weakest part, because its script is not in the repo.

## Tooling experience

- **Worked:** Capturing the baseline before touching code, raw and formatted,
  then comparing hashes after every commit. It caught nothing, which is the
  point, and it made the history rewrite safe to do. Message snapshots caught
  the one real regression: moving GeneratorSettings to Schema.Class wrapped
  the issue tree in an Encoding node, and the formatted errors fell back to
  the generic branch.
- **Didn't:** Running the integration suites from a parallel worktree is not
  practical, since each suite has its own node_modules and lockfile. Per-commit
  verification of the rewritten history relied on tree equivalence with
  already-verified commits instead of reruns.
- **Frustrating:** `pkill -f` with a pattern that also matched the invoking
  shell's command line killed the verification shell (exit 144).
- **Wished existed:** A repo script for the invariance check, and a way to
  run one integration suite against an arbitrary built dist/.

## Implementation improvement opportunities

- One operation-to-error table in the templates (see findings).
- Unknown option keys pass decoding silently; `onExcessProperty: "error"` would
  catch typos but is a behaviour change.
- The provider allow-list for createManyAndReturn is still hard-coded.
- `tests/acquireUseReleaseWithErrors.test.ts` is not run by any command.

## Goal & prompt critique

- Replace the concurrency requirement with "write through one service; add
  concurrency only if more than one file is emitted".
- Add to SPEC Constraints from the start: "Expected failures are
  Schema.TaggedError; every dependency is a Context.Service provided by a
  Layer." That line would have avoided the rewrite of errors.ts and output.ts.
- Name the invariance script as a deliverable, not only its result.

## TODOs worth codifying

- Pinned Biome.
- A standard line: "load effect-first and schema-first skills before the first
  line of Effect code".

## Lessons (confidence-tiered)

- **HIGH — Critical:** Capture the baseline before the first code change —
  invariance can only be proven against output recorded from the untouched
  code, and it is what made a later history rewrite verifiable by tree diff.
- **MEDIUM — Best practice:** Snapshot user-facing error messages, not just
  failure — a schema refactor changed the issue tree shape without changing
  any test that only asserted failure.
- **LOW — Consideration:** Unstable Effect modules (effect/unstable/cli) rename
  APIs between RCs — keep their use confined to scripts, as here.
